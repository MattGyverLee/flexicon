THE QUESTION (spec.md:215-221)
  "With FLEx holding the project, does a Phase 1 Transaction inside the flexlibs
   non-undoable task actually commit on the host save, or does it need an
   explicit MainCacheAccessor flush? Run a SetGloss through an attached view
   under real FlexTools, close FlexTools, reopen, assert the value persisted.
   If it does not persist, this spec is wrong that _undoable = False alone is
   sufficient, and CP3 must block CP1 from shipping."

ANSWER
  It persists. No explicit flush is needed. The spec's claim that
  _undoable = False alone is sufficient HOLDS.

--------------------------------------------------------------------------------
WHY THIS IS "REAL FLEXTOOLS" AND NOT AN IMITATION
--------------------------------------------------------------------------------
The gate was driven from the CLI through FlexTools' OWN code path -- the same one
the GUI's Run button uses. A thin driver calls:

    flextoolslib.code.FTModules.ModuleManager()
        .LoadAll()
        .RunModules(projectName, [moduleName], reporter, modifyAllowed=True)

RunModules() is the GUI's entry point. Internally
(C:\Python313\Lib\site-packages\flextoolslib\code\FTModules.py):

  * __openProject()  -> FLExProject.OpenProject(name, writeEnabled=modifyAllowed)
                        using the STABLE flexlibs class, exactly as the GUI does
  * per module       -> FlexToolsModuleClass.Run(project, reporter, modifyAllowed)
  * __closeProject() -> FLExProject.CloseProject()
                        docstring: "Save any changes and release the LCM Cache."

That CloseProject() is the host save under test. Gate A ran in ONE process which
then exited (FLExCleanup); Gate B ran in a SEPARATE, LATER process. That is
"run under FlexTools / close FlexTools / reopen FlexTools" faithfully, with a
real process boundary rather than a re-read of a warm cache.
