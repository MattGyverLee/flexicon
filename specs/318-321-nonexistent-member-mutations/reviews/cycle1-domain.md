## DESIGN DECISIONS REQUIRED

1. **#319 Participants -- a two-hop navigation change, not a rename.** `record.Participants` never existed; the real graph is `IRnGenericRec --OC(ParticipantsOC)--> IRnRoledPartic --RC(ParticipantsRC)--> ICmPerson`, with `IRnRoledPartic.RoleRA` carrying an optional role tag. Consequences the programmer must decide before coding:
   - `GetParticipants` must flatten: iterate `record.ParticipantsOC`, union each group's `ParticipantsRC`. Do we also expose the associated Role per person, or return a flat person list (losing role info) as the current signature (`list[ICmPerson]`) implies?
   - `AddParticipant`/`RemoveParticipant` need a target `IRnRoledPartic` to mutate. If `record.DefaultRoledParticipants` is null (no roled-partic group yet), a **new object must be created** via `record.MakeDefaultRoledParticipant()` before a person can be added -- object creation with write-transaction implications, entirely absent from the current (broken) code shape. Decide: always use the "default" (no-role) group, or require callers to pass/select a Role? The current API has no `role` parameter, so as written it can only sensibly target the default group.
   - `RemoveParticipant` must search across **all** `IRnRoledPartic` groups owned by the record (a person could appear in more than one role-group) and remove from whichever contains them -- not just the default one.
   - `ParticipantsRC` is a reference collection, so Add/Remove never touch the `ICmPerson`'s lifetime -- but Add/Remove *on* `ParticipantsOC` (the `IRnRoledPartic` groups themselves) would be ownership-affecting and destructive, same as #318's Remove-is-Delete semantics. These must not be conflated.

2. **#318 Remove vs Delete -- resolved, not open**, but flag loudly for the fix author: `OS.Remove(dupe)` on `PronunciationsOS`/`AlternateFormsOS`/`ExamplesOS` **is** the correct deletion primitive (per `RemoveOwnee`'s documented destructive behavior) -- do **not** additionally call `dupe.Delete()`/`DeleteUnderlyingObject()`, which would double-free/throw. This is the opposite risk from orphaning: adding an extra explicit delete on top of `.Remove()` would be the new bug introduced while patching.

3. **#320 Overlay Elements -- validation gap, UNVERIFIED against index.** `PossItemsRC` is confirmed as the correct backing for "overlay elements," but the reflection data carries no constraint metadata for whether a `ICmPossibility` added via `AddElement` must already be a member of the list pointed to by `overlay.PossListRA`. FLEx's UI most likely enforces "element must belong to the overlay's list," but that is a UI/business rule, not visible in static LCM reflection, so it is **UNVERIFIED** here -- the fix author should add an explicit membership check before allowing `AddElement` to insert into `PossItemsRC`, rather than shipping an unconstrained add that the real FLEx UI would reject.
